# Conversation and Scope

Resolve the workspace using local-persistence.md first, then read this reference for every job-search request. Commands are shortcuts; users can speak naturally. Route to existing workflows without asking them to select internal commands.

| Request | Workflow and scope |
|---|---|
| Help me get started | setup |
| What needs my attention? / Show my jobs | check; local only |
| Find five remote roles | find; five qualified results, remote preference for this run |
| Help me apply here / Track this link | find for manual intake, then apply only if requested |
| Prepare three applications / Tailor this resume | apply; prepare-only, no uploads, sends, or submissions |
| Follow up on referrals | referral; prepare drafts, review before sending |
| I have 15 minutes / Help with my search today | daily; respect the stated time or count |
| Continue / Resume | read profile/session.md, then resume the recorded workflow |

There is no new `jobs add` or `jobs update` command. Explicit status corrections may update the CSV after identifying the intended row; never invent a successful submission.

## Scope Before Work

Honor explicit targets, counts, time limits, and prepare-only requests. Do not expand a specific request into a full daily run. State a short scope and start; do not ask permission for reversible local preparation.

For an unspecified daily run, start with up to three distinct jobs, prioritizing existing deadlines and ready work; discover only enough to fill unused places. This is a batch limit, not a requirement to find new jobs every day. Count each distinct job once across workflows. Stop before starting another job after the limit; do not send unlimited outreach within a selected job (default at most one proposed outreach action per selected job). An explicit user scope overrides these defaults.

For time limits, check elapsed time between operations; estimates are approximate and a browser operation may overrun. Checkpoint and summarize at the limit. Do not promise background execution, scheduled continuation, or completion while waiting for an answer.

## Local and Browser Readiness

Local work includes tracker checks, resume intake, preference setup, drafting from saved job descriptions, document preparation, and reviewing saved outreach logs. It needs no browser preflight. Each step still needs its relevant source data; ask for a missing resume or job description only when that step needs it.

Before browser-dependent discovery, live reply checks, uploads, messages, or application forms, run browser-preflight.md. If it fails, checkpoint that step and continue useful local work within scope. Use the built-in browser by default or the explicitly selected browser, and verify the relevant account. Switching browsers requires identity revalidation; do not assume shared sessions. LinkedIn-first discovery and its explicit fallback approval remain in force.

## Preference Feedback

Use explicit feedback to improve matches. “Too junior; stop showing junior roles” can update resumes/search_profile.md with that rule and a short feedback note. “Skip this job” excludes only that job, recorded in tracker Notes if tracked or the search profile if untracked. Do not turn a one-job rejection into an industry-wide or company-wide ban. Ask a short clarification if broader intent is ambiguous, while continuing independent work.

Distinguish a one-run filter from a durable preference. Summarize any saved preference change. Never infer sensitive eligibility or personal facts from feedback, names, or resume context.
